# ledkit Milestone 4: ESP32 RMT backends Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver `ledkit-esp-idf` (ESP-IDF, `std`) and `ledkit-esp` (esp-hal, `no_std`): NeoPixel-type LEDs driven by the ESP32's RMT peripheral. Prove both on the ESP32-C6 DevKit, and move the pulse project (the first consumer) onto `ledkit-esp-idf`.

**Architecture:** `ledkit-core` gains the RMT/PIO-shaped pieces that the backends must not re-derive: `BitPulse` (one bit as `u16` high/low ticks), `PulseTicks::{zero_pulse, one_pulse, bit_pulses}`, and `ResetGap` (how long to wait before the next frame). `ledkit-esp-idf` is a port of the pulse project's `RmtOutput`. It feeds wire bytes to ESP-IDF's RMT bytes encoder, and it enforces the reset gap with `std::time::Instant` plus `ResetGap`. `ledkit-esp` converts pixels into a user-supplied buffer of esp-hal `PulseCode`s. It appends a low reset code and the end marker, so each transmission already includes the reset gap, as the SPI backend does. Both crates are built only for ESP targets, so they sit outside the host workspace, the same way the examples do.

**Tech Stack:** Rust; `ledkit-core` (`no_std`, MSRV 1.82). `ledkit-esp`: esp-hal 1.x with `unstable` (RMT is an unstable driver in esp-hal 1.2), target `riscv32imac-unknown-none-elf`, stable Rust ≥ 1.95. `ledkit-esp-idf`: esp-idf-hal 0.47 (the combined `esp-rs/esp-idf` git repository, as pulse uses), target `riscv32imac-esp-espidf`, nightly with `build-std`, ESP-IDF v5.5.

**Spec:** `docs/superpowers/specs/2026-10-25-ledkit-design.md` ("Crates": `ledkit-esp`, `ledkit-esp-idf`; "Decided: who sets up the hardware"; "Constraints"; phasing note on `ledkit-esp-idf`). **Roadmap:** `docs/superpowers/plans/2026-10-25-ledkit-roadmap.md`, the RMT note under "Notes for the milestone 3 plan" and "Notes from the first consumer" (reset gap, RMT tick type).

## Global Constraints

- License `MIT OR Apache-2.0`. Each new crate copies `LICENSE-MIT`, `LICENSE-APACHE` and a `NOTICE` like `ledkit-spi`'s.
- `ledkit-core` stays `#![cfg_attr(not(test), no_std)]`, with no allocation, no nightly and MSRV 1.82. It must still build for `thumbv6m-none-eabi` and `riscv32imc-unknown-none-elf`.
- `ledkit-esp` is `#![no_std]` with no allocation and no nightly. `ledkit-esp-idf` is `std`; the ESP-IDF target needs nightly, which is an upstream requirement.
- **The user's program does the normal HAL setup and hands ledkit a peripheral and a pin.** Each backend offers a one-line constructor taking the RMT channel (or pin) and the clock it runs from.
- Backends use `ledkit-core`'s `wire` and `encode` helpers. They never re-implement color order or timing math, and never apply brightness or gamma.
- **The backend owns the reset gap** (`Output` docs). Consecutive frames are at least `reset_us` apart, however often `show()` is called.
- A clocked chip (DotStar) on an RMT backend is a compile error, through `const { ClocklessTiming::of::<C>() }`.
- Every public item has a plain-English doc comment and an example. `missing_docs` and `clippy::pedantic` apply, with `-D warnings`. The two ESP crates sit outside the workspace, so each copies the workspace `[lints]` table into its own `Cargo.toml`.
- Each ESP crate implements `smart-leds-trait` 0.3 behind a `smart-leds` feature, the same way `ledkit-spi` does.
- **Never use `docs.esp-rs.org`** (hijacked). Use `https://docs.espressif.com/projects/rust/esp-hal/`, `https://docs.espressif.com/projects/rust/book/`, and for ESP-IDF, `https://esp-rs.github.io/std-training/` and `github.com/esp-rs/esp-idf`.

## Decisions this plan makes

- **The RMT tick rate is 10 MHz** (100 ns) in both backends, the same as pulse. `PulseTicks` at 10 MHz is already validated for every clockless chip. `ledkit-esp` derives its channel divider from the RMT source frequency the user passed to `Rmt::new` (normally 80 MHz, so a divider of 8). A frequency that isn't a whole multiple of 10 MHz in the range 10 MHz to 2.55 GHz is a `TimingError`-style error from `new`.
- **`u16` ticks come from core.** `BitPulse { high: u16, low: u16 }` removes the cast the consumer had to write. Backends ask for `pulse_ticks(10_000_000, RMT_MAX_TICKS)` with a backend-private `RMT_MAX_TICKS: u32 = 32_767` (the RMT's 15-bit length field).
- **The reset gap:**
  - **`ledkit-esp`** appends one low `PulseCode` covering the reset (split over its two halves, each ≤ 32 767 ticks; never a zero length, which the RMT reads as "end"), then the end marker. `transmit(..).wait()` returns after the reset, so back-to-back `show()` calls are safe, as with SPI.
  - **`ledkit-esp-idf`** can't append a reset to ESP-IDF's bytes encoder. It records an `Instant` when each send completes. Before the next send it sleeps for `ResetGap::remaining_us(elapsed)`, so it only waits when frames come faster than the reset time.
- **Buffers:**
  - `ledkit-esp` takes a user buffer `B: AsMut<[PulseCode]>`, sized by `const fn ledkit_esp::buffer_len::<C>(led_count) = led_count * C::ORDER.len() * 8 + 2`. That is 4 bytes per bit, so 300 LEDs is about 29 KB, which is fine on ESP32s. A buffer that's too small gives `Error::BufferTooSmall { needed }` and sends nothing.
  - `ledkit-esp-idf` keeps a reused `Vec<u8>` (allowed under `std`), as pulse does.
- **Both crates are excluded from the root workspace.** Root `Cargo.toml` gets `exclude = ["examples", "crates/ledkit-esp", "crates/ledkit-esp-idf"]`. The host workspace can't build esp-hal or ESP-IDF. Each crate is checked by building its example for the target, locally and in CI.
- **Chip selection:**
  - `ledkit-esp` forwards esp-hal's chip features: `esp32`, `esp32c3`, `esp32c6`, `esp32h2`, `esp32s2`, `esp32s3`, the same convention as `esp-hal-smartled`. Users write `ledkit-esp = { …, features = ["esp32c6"] }`.
  - `ledkit-esp-idf` needs no chip feature, because `MCU` in the app's `.cargo/config.toml` selects it.
- **Async:**
  - `ledkit-esp` implements `OutputAsync` for esp-hal's async TX channel.
  - `ledkit-esp-idf` is blocking only; ESP-IDF users have threads. Async there is deferred and recorded in the roadmap.
- **Names:**
  - Both crates export `RmtOutput`, the name pulse already uses, so switching is an import change.
  - Error types: `ledkit_esp::Error { Timing(TimingError), Rmt(esp_hal::rmt::Error), Config(esp_hal::rmt::ConfigError), BufferTooSmall(BufferTooSmall) }` and `ledkit_esp_idf::Error { Timing(TimingError), Esp(EspError) }`. Both implement `Display`, `core::error::Error` / `std::error::Error`, and `From` for each inner type.
- **Xtensa (ESP32, S2, S3) is build-untested and hardware-untested in this milestone.** The owner has no S3 on hand, and CI would need `espup`. The roadmap's hardware follow-ups record it.

## Review Focus

1. **Back-to-back `show()` faster than the reset time.** With `ledkit-esp`, frames must still latch, so the reset code must be in the pulse train. With `ledkit-esp-idf`, the second `show()` must wait out the rest of `reset_us`. Pinned by Task 1's `ResetGap` tests and by Task 3's encoder test, which checks for the trailing reset code.
2. **A zero-length pulse is the RMT end marker.** The reset code must never contain a 0 length, even for a chip whose reset splits unevenly. Pinned in Task 3 for every clockless chip in the catalogue.
3. **The buffer is smaller than the strip.** Users get `Error::BufferTooSmall { needed }`, nothing is sent, and nothing panics. Pinned in Task 3.
4. **An RMT source clock ledkit can't divide down to 10 MHz** (for example a 32 MHz ESP32-H2 or a typo). Users get a clear error from `new`, not wrong colors. Pinned in Task 3.
5. **Zero LEDs.** `show()` on `Strip<_, 0, _>` sends only the reset, without panicking. Pinned in Tasks 1 and 3.

- `pub struct BitPulse { pub high: u16, pub low: u16 }` (`Copy`, `Debug`, `PartialEq`, `Eq`), in `encode`.
- `impl PulseTicks`:
  - `pub const fn zero_pulse(&self) -> BitPulse`
  - `pub const fn one_pulse(&self) -> BitPulse`
  - `pub fn bit_pulses(&self, wire: impl IntoIterator<Item = u8>) -> impl Iterator<Item = BitPulse>`, which yields 8 pulses per byte, most significant bit first.

- `pub struct ResetGap { reset_us: u32 }`, exported at the crate root:
  - `pub const fn of<C: Chip>() -> Self` (a compile error for clocked chips, via `ClocklessTiming::of`)
  - `pub const fn reset_us(&self) -> u32`
  - `pub const fn remaining_us(&self, elapsed_us: u64) -> u32`, which is the wait still needed before the next frame: `reset_us - elapsed`, floored at 0.
