# ledkit Milestone 5: `ledkit-rp`, the RP2040 / RP2350 PIO backend

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver `ledkit-rp`: NeoPixel-type (clockless) LEDs driven by the PIO of the RP2040 and RP2350, fed either by the processor (TX FIFO) or by DMA, blocking and async. Ship examples for the Raspberry Pi Pico 2 W (Arm and RISC-V cores) and the Adafruit Feather RP2040 SCORPIO, ready for the owner's by-eye hardware checks (T1–T4 and T10 of the hardware test plan on branch `esp32s3`).

**Architecture:** `ledkit-core` gains the two PIO-shaped pieces a backend must not re-derive: a **PIO step timing search** (`ClocklessTiming::pio_timing`, returning `PioTiming`, on top of the shared equal-period search `equal_period_ticks`), and **word packing** for a shifting FIFO (`fill_pio_words`, `pio_word_count`). `ledkit-rp` installs the standard 4-instruction WS2812 program (side-set, three delays T1/T2/T3 computed from the chip's datasheet windows at the real system clock), configures one state machine, and implements `Output` and `OutputAsync` twice: `PioOutput` (the processor pushes words into the TX FIFO) and `PioDmaOutput` (a DMA channel streams a `'static` word buffer into the FIFO). The reset gap is timed with the chip's 1 MHz timer.

**Tech Stack:** Rust stable (1.82+ for the crate). `rp2040-hal` 0.12 (feature `rp2040`, `thumbv6m-none-eabi`) and `rp235x-hal` 0.4 (feature `rp235x`, `thumbv8m.main-none-eabihf` and `riscv32imac-unknown-none-elf`), `pio` 0.3 (the version both HALs use). `ledkit-core` stays `no_std`, MSRV 1.82.

**Spec:** `docs/superpowers/specs/2026-10-25-ledkit-design.md` ("Crates": `ledkit-rp`). **Roadmap:** `docs/superpowers/plans/2026-10-25-ledkit-roadmap.md`, the PIO and reset-gap notes under "Notes for the milestone 3 plan". **Acceptance:** `git show esp32s3:docs/superpowers/plans/2026-11-02-hardware-test-plan.md`, the Pico 2 W and SCORPIO sheets.

**Starting point:** branch `m5-rp` from `main` (after milestone 7). Models: `crates/ledkit-esp` (a `no_std` pulse backend outside the workspace, its docs, `Error`, smart-leds impls) and `examples/esp32c6-rmt`; the round structure of `examples/esp32s3-check` on branch `esp32s3`.

## Global Constraints

- License `MIT OR Apache-2.0`; the crate copies `LICENSE-MIT`, `LICENSE-APACHE` and a `NOTICE`.
- `ledkit-rp` is `#![no_std]`, no `alloc`, stable Rust. It sits **outside the root workspace** (like `ledkit-esp`): the HALs only build for their targets. It is built and linted for each target in CI, and through its examples.
- Backends use `wire` and `encode`; never re-implement color order or timing maths; never apply brightness or gamma.
- **The user's program does the HAL setup** (clocks, `PIO::split`, DMA `split`, the pin's PIO function) and hands ledkit a state machine, a pin, the system clock rate and the timer. One constructor call.
- A clocked chip (DotStar) is a compile error, via `const { ClocklessTiming::of::<C>() }`.
- Every public item has docs and an example; `missing_docs` and `clippy::pedantic` with `-D warnings`; the workspace lint table is copied into the crate's `Cargo.toml`.

## Decisions this plan makes

- **HAL: `rp2040-hal` and `rp235x-hal`, not embassy-rp (for now).** One crate with a chip feature, `rp2040` or `rp235x` (exactly one; a `compile_error!` says so otherwise), aliased internally as `hal`. The two HALs share their PIO, DMA and timer APIs almost line for line, so the code is written once. embassy-rp 0.10 depends unconditionally on `cortex-m` / `cortex-m-rt`, so it **cannot build for the RP2350's Hazard3 RISC-V cores**, and the RISC-V build is a requirement of this milestone. An embassy-rp flavour (interrupt-driven async, and the only way to run the CYW43 Wi-Fi driver for check T11) is a follow-up, Arm only.
- **Two outputs, both first-class:**
  - `PioOutput`: the processor pushes one word per LED into the state machine's TX FIFO (joined to 8 entries). Nothing to set up beyond the state machine; good for short strips and small programs. A long interrupt mid-frame can starve the FIFO; the line then sits low longer than the reset time and the frame splits (check T8 shows this).
  - `PioDmaOutput`: a DMA channel, paced by the state machine's DREQ, streams the frame. The processor only fills the buffer. The buffer must be `&'static mut [u32]` (DMA needs memory that outlives the transfer); `static_cell` provides it on both Arm and RISC-V.
- **Blocking and async on the same types.** Both outputs implement `Output` and `OutputAsync`; nothing in the HAL types distinguishes the two. rp-hal has no async PIO or DMA, so async waits by **yielding** to the executor between checks (FIFO has room, DMA done, reset gap over) instead of sleeping on an interrupt. It works with any executor and lets other tasks run during a DMA frame; it does not let the core sleep. Documented plainly; interrupt-driven async waits for the embassy-rp follow-up. An async frame dropped mid-way (for example in `select`) is finished by the next call (DMA) or leaves a partial frame (CPU-fed), as with `ledkit-esp`.
- **Equal-period timing, in `ledkit-core::encode`.** The standard PIO program sends every bit in the same number of cycles: high for T1, then high (a `1`) or low (a `0`) for T2, then low for T3. `PulseTicks` doesn't guarantee equal periods (WS2812B at 10 MHz is 13 vs 14 ticks).
  - The equal-period search itself is **shared with the nRF PWM backend**: `ClocklessTiming::equal_period_ticks(ticks_per_second, max_period) -> EqualPeriodTicks { period, zero_high, one_high }`, written on branch `nrf` (commit `bec40b5`) and cherry-picked here so the two branches merge without a clash. It checks every candidate exactly against all four windows and picks the highs closest to typical, then the period closest to the typical bit, then the shorter period. Error: `TimingError::EqualPeriodUnusable`.
  - `ClocklessTiming::pio_timing(sys_hz, max_step, max_divider) -> PioTiming { divider, high, data, low, reset_us }` (new file `encode/pio_timing.rs`) loops over **whole dividers that divide the system clock exactly** (so the tick rate is an exact integer and every window check stays exact), maps T1 = `zero_high`, T2 = `one_high - zero_high`, T3 = `period - one_high`, rejects steps outside 1..=`max_step`, and keeps the divider whose four pulses are closest to typical (ties to the smaller divider). ledkit-rp calls it with `max_step = 16` (a delay field with one side-set bit holds 0–15) and `max_divider = 65_535`. Fractional dividers are never used: they make pulse widths jitter by a cycle.
  - Pinned by tests: every clockless chip in the catalogue at 125, 133, 150 and 200 MHz, all four pulses inside their windows; too slow a clock is refused; it runs in a `const`.
- **Words: one LED per FIFO word.** Autopull with a threshold of 8 bits per channel (24 for RGB, 32 for RGBW), shifting left, so each word carries one pixel's wire bytes, most significant byte first. A frame is exactly `led_count` words, no partial word ever sends stray bits, and RGB and RGBW need nothing special. RAM cost 4 bytes per LED (400 bytes for 100 LEDs). Core helpers `fill_pio_words(wire, bytes_per_word, &mut [u32])` and `pio_word_count(bytes, bytes_per_word)` do the packing and are host-tested; chips with more than 4 channels are refused at compile time.
- **The reset gap.** The program idles with the line low whenever the FIFO is empty. Each write first waits until `ResetGap::remaining_us` (measured from the end of the previous frame) is zero, then sends. The end of a frame is the moment the FIFO is empty plus at most one word still in the shift register; ledkit waits that bound (`(bits per word + 1) × bit period`, computed once in `new`) before returning, so `show()` returns only when the data is out (CONTRIBUTING step 4), and records that time as the frame end. No reliance on the sticky stall flag. Time comes from the HAL's `Timer` through a tiny `MicrosecondClock` trait that ledkit implements for `rp2040_hal::Timer` and `rp235x_hal::Timer<D>` (both `Copy`).
- **RGBW (SK6812 RGBW) works unchanged**: 32-bit words, threshold 32 (written as 0 in the 5-bit field). Tested on the host by the word packing tests; hardware pending.
- **CYW43 on the Pico 2 W.** Its driver (embassy's `cyw43-pio`) conventionally takes PIO0 state machine 0 and DMA channel 0, and the radio uses GPIO23/24/25/29. ledkit never claims anything itself: the user hands it a state machine and a DMA channel. The `rp2350-pio` example deliberately uses **PIO1 state machine 0, DMA channel 1 and GPIO16**, leaving PIO0, DMA0 and the radio pins free; the crate docs say so. rp-hal has no CYW43 driver, so T11 (radio on) waits for the embassy-rp follow-up.
- **Program memory.** Each output installs its own 4-instruction program (32 slots per PIO), so up to 4 strips per PIO block today, plenty for these boards. Sharing one installed program between state machines (8 SCORPIO channels on two PIOs) is a follow-up, along with parallel output.
- **Unsafe code.** The DMA path needs to hand the DMA engine a *prefix* of the buffer (frames shorter than the buffer, for the 1–150 LED sweep) and get the whole buffer back afterwards. rp-hal only accepts `ReadTarget`s, so `ledkit-rp` implements `ReadTarget` for a small `DmaFrame { words: &'static mut [u32], len }`, the one `unsafe impl` in the crate, with a SAFETY note. The crate's lint is `unsafe_code = "deny"` with one documented `allow`.
- **DotStars on these chips.** DotStars (APA102, SK9822) have a clock wire, so the one-wire PIO program can't drive them, and `ledkit-rp` refuses them at compile time. `ledkit-spi`'s `ClockedSpi` works on any `embedded-hal` 1.0 SPI bus, which rp-hal's `Spi` is, so no RP-specific code is needed. Both examples get a DotStar round (owner's request, 2026-11-02): SPI0 with data on GPIO19 and clock on GPIO18 (level-shifted channels on the SCORPIO; the 74AHCT125 on the Pico 2 W), the shared pattern at 4 MHz, then a clock sweep from 1 to 32 MHz. A PIO-clocked DotStar output is a follow-up, only if SPI pins become a constraint.
- **smart-leds**: `SmartLedsWrite` and `SmartLedsWriteAsync` for both outputs behind `smart-leds`, colours sent as given (like `ledkit-esp`).
- **Errors**: `ledkit_rp::Error { Timing(TimingError), NoProgramSpace, BufferTooSmall(BufferTooSmall), ChannelLost }`. `ChannelLost` only appears if a panic unwound mid-send. A chip with more than 4 channels is a compile-time error, not a variant.

## Review Focus

1. **Equal periods** for every clockless chip in the catalogue at 125, 133, 150 and 200 MHz, all four pulses inside their windows (Task 1 tests).
2. **Back-to-back `show()`**: the second frame must wait out the reset gap measured from the real end of the first, including the last word still shifting (Task 3 code; T2 on hardware).
3. **Short frames on DMA** (sweep 1–150): only `len` words go out, the buffer comes back whole, a buffer that is too small gives `BufferTooSmall` and sends nothing.
4. **RISC-V**: the crate and the `rp2350-pio` example build for `riscv32imac-unknown-none-elf` as well as Arm.
5. **Zero LEDs**: `show()` on a strip of 0 sends nothing and does not hang.
